# Nexo Server CLI: one download to host a server

**Status:** Draft · **Date:** 2026-11-08 · **Scope:** a standalone `nexo-server` program, Windows first, Linux and
macOS from the same code · **Related:** [SERVER.md](SERVER.md) (today's manual setup), [SPEC.md](SPEC.md)

## 1. Why

Hosting Nexo today means Node, Docker, a `.env` with matching LiveKit secrets, a LiveKit config, and on
Windows a WSL distro with its own networking quirks. Only someone comfortable with all of that can host.

The goal: **a friend downloads one file, runs it, answers two questions, and sends an invite to the group.**
The host can play from the same PC: their Nexo app joins their own server like everyone else.

The server stays **separate from the desktop app**: friends who only play never download server code, the
server can run on a different PC (an old laptop, a VPS) with no client installed, and it has its own release
artifact and lifecycle.

### Goals

- One download per OS: `Nexo-Server-<version>-win-x64.zip` (Windows first), then Linux x64 and macOS.
- No prerequisites: no Node, no Docker, no WSL, no hand-written config.
- First run is a short interactive setup. After that, double-click (or `nexo-server`) just starts it.
- It tells the host, in plain words, how friends can reach it, and what to do when they can't.
- Same data format and behavior as today's server: an existing host can move to the CLI and keep its data.

### Non-goals (for now)

- A GUI. It's a console program with clear output. (A tray icon is a possible later step.)
- Hosting relays or anything in the cloud. Reachability is solved on the host's side (§6).
- Changing the server's features or protocol. The CLI wraps the existing server.

## 2. Decisions

| # | Decision | Why |
|---|---|---|
| C1 | **Standalone CLI**, not built into the desktop app | Players don't carry server code; the server can run on another machine; independent lifecycle |
| C2 | **Node single executable** (SEA): the server bundled with esbuild into one JS file, injected into the Node binary | No Node install. The server only needs `socket.io`, `livekit-server-sdk` and `node:sqlite` (built in; verified on Node 24.22) |
| C3 | **LiveKit's native binary** shipped next to it (`livekit-server.exe`, pinned version + SHA-256, same pin as `docker-compose.yml`) and run as a child process | LiveKit publishes Windows/Linux/macOS builds (`livekit_1.13.11_windows_amd64.zip`). No Docker |
| C4 | One process tree: the CLI runs the Nexo server **in-process** (`start(config)` from `server/src/server.ts`) and supervises LiveKit | Simple lifecycle: Ctrl+C stops both; a LiveKit crash is restarted |
| C5 | Config in a JSON file in the data folder, generated by setup; env vars still override | Hosts never see LiveKit keys; today's `.env` keeps working |
| C6 | Distributed as a **zip**, attached to the same GitHub release as the app | Same versioning and release workflow; no installer needed for a CLI |

## 3. User experience

### 3.1 First run

The host unzips and double-clicks `nexo-server.exe` (or runs it in a terminal). With no config yet:

```

  Password for new friends (Enter = generate one) [moss-tiger-41]:

  Data folder: C:\Users\ana\AppData\Local\Nexo Server
  Saved. Starting…

  ✓ Nexo server   listening on port 3001
  ✓ Voice (LiveKit) ready on ports 7880–7882
  ✓ Router: opened ports automatically (UPnP)
  ✓ Public address: 187.12.34.56

  Invite your friends — send them this:
  ┌──────────────────────────────────────────────┐
  │ Server:   http://187.12.34.56:3001           │
  │ Password: moss-tiger-41                      │
  └──────────────────────────────────────────────┘
```

Then it shows a small live status block (refreshed every few seconds, only when it changes):
`3 online · 2 in voice · 1 streaming · upload 9.4 Mbit/s`.

### 3.2 Later runs

Double-click starts directly with the saved config and prints the invite again.

### 3.3 Commands

| Command | Does |
|---|---|
| `nexo-server` | Start (runs setup first if there's no config) |
| `nexo-server setup` | Run setup again (name, password, ports) |
| `nexo-server invite` | Print the invite (addresses + password) |
| `nexo-server status` | Is it running, who's online, ports, version |
| `nexo-server rename-user <old> <new>` | Free a name (replaces the manual SQLite command in SERVER.md "Lost identity") |
| `nexo-server backup [file]` | Consistent copy of the database (SQLite `VACUUM INTO`) |
| `nexo-server autostart on\|off` | Start with Windows (per-user, no admin) / install a systemd unit on Linux |
| `nexo-server update` | Download and swap in the newest server release (§8) |
| `--data <dir>` | Use another data folder (several servers, or an existing `server/data`) |

## 4. Architecture

```
nexo-server.exe  (Node SEA: CLI + bundled Nexo server)
 ├─ CLI: setup, config, status, networking (UPnP, STUN, Tailscale detection), supervision
 ├─ Nexo server (in-process): http + socket.io on :3001, SQLite in <data>/nexo.db
 └─ child: livekit-server.exe --config <data>/livekit.yaml   (:7880 tcp, :7881 tcp, :7882 udp)
```

- **Config file** `<data>/config.json`: `serverName`, `serverPassword`, `port`, LiveKit `apiKey`/`apiSecret`
  (random 32+ bytes, generated once), ports, network mode (§6). Env vars with today's names (`PORT`,
  `SERVER_PASSWORD`, `LIVEKIT_*`, …) override it, so `.env`-based hosts can switch without changes.
- **LiveKit config** `<data>/livekit.yaml` is **generated on every start** from config.json (keys, ports,
  `node_ip` / `use_external_ip` per §6). The repo's `livekit.yaml` stays the template, so Docker and CLI
  setups behave the same.
- **Data folder**: Windows `%LOCALAPPDATA%\Nexo Server`, Linux `~/.local/share/nexo-server` (or
  `/var/lib/nexo-server` as a service), macOS `~/Library/Application Support/Nexo Server`. Holds the DB,
  attachments and avatars (as today under `DATA_DIR`), config, generated LiveKit config, logs.
- **Supervision**: LiveKit restarts with backoff if it exits; repeated crashes are reported in the console.
  Ctrl+C / SIGTERM stops the Nexo server gracefully (existing `server.close()`), then LiveKit.
- **Single instance** per data folder (lock file), so a second double-click says "already running" and prints
  the invite instead of failing on ports.
- **Logs**: console plus a rotating `<data>/logs/nexo-server.log` (for bug reports).

## 5. Ports

| Port | Proto | Use |
|---|---|---|
| 3001 | TCP | Nexo server (http + socket.io) |
| 7880 | TCP | LiveKit signaling |
| 7881 | TCP | LiveKit ICE/TCP fallback |
| 7882 | UDP | LiveKit media (single port) |

All configurable in setup. Windows asks once to allow `nexo-server.exe` / `livekit-server.exe` through the
firewall; setup explains this before it happens ("click **Allow** on both, private and public networks").

## 6. Reachability (the hard part)

Friends must reach the host's PC. The CLI tries, in order, and **tells the host the result in plain words**:

1. **Same network** (LAN addresses): always printed, works for people in the same house.
2. **Tailscale**: if the host is on Tailscale (a `100.64.0.0/10` interface, or `tailscale ip -4`), print that
   address as the recommended invite. LiveKit advertises it (`node_ip`).
3. **Router port forwarding via UPnP**: ask the router to forward the ports in §5 (lease renewed while
   running, removed on exit). Then:
   - Router's external IP (UPnP `GetExternalIPAddress`) vs. the public IP seen by a **STUN** server
     (LiveKit already uses STUN; same servers).
   - **Equal** → port forwarding should work: print the public invite, set LiveKit `use_external_ip: true`.
   - **Different, or the router's IP is in `100.64.0.0/10`** → **CGNAT**: the ISP shares one public IP among
     many customers, and no port forwarding can work. Print: "Your internet provider doesn't let friends
     connect to you directly. Use Tailscale instead:" and a short Tailscale walkthrough (install, log in,
     share the machine with friends), the same steps as SERVER.md.
   - **UPnP unavailable** → print the manual port-forwarding table (§5) and the Tailscale option.
4. Whatever mode is chosen is saved (`network.mode: auto | tailscale | public | lan`) and can be forced in setup.

**Verifying from outside** needs a second machine on another network. The CLI can't fully prove it alone
(open question Q3); it gives its best judgment (UPnP ok + no CGNAT → "should work") and the final test is a
friend joining. The status line shows when the first remote friend connects ("✓ a friend connected from
outside").

**The host on the same PC** joins with `http://localhost:3001` (printed separately). The public address
might not work from inside the host's own network (routers without NAT loopback); localhost always does.

## 7. Bandwidth and resources

- CPU: small (the Nexo server is light; LiveKit forwards, never transcodes).
- **Upload is the limit.** Every viewer of a stream receives it through the host's connection (four viewers of
  a 1080p60 stream ≈ 32 Mbit/s up). The status line shows live upload; above ~80% of a measured or configured
  limit, it warns and suggests a lower stream quality. (SERVER.md "Bandwidth" has the numbers.)
- The PC must stay on: setup mentions it; on Windows the CLI asks the OS not to sleep while friends are
  connected (`SetThreadExecutionState`), not while the server is idle.

## 8. Releases and updates

- The release workflow builds `nexo-server` per OS with the app (same tag, same version) and attaches
  `Nexo-Server-<version>-win-x64.zip` (+ `-linux-x64.tar.gz`, `-mac-*.tar.gz` later): `nexo-server(.exe)`,
  `livekit-server(.exe)`, `LICENSE` + LiveKit's license, a short `README.txt`.
- **Version compatibility**: the protocol is additive so far (beta.2 server works with beta.1 apps). The
  server announces its version; a much newer app can tell the user "ask your host to update the server".
- **`nexo-server update`**: checks GitHub releases (same lanes as the app: stable/beta, no test builds unless
  the server itself is a test build), downloads the zip for this OS, verifies its SHA-256 (published next to it),
  swaps the files, restarts. On start, the CLI prints one line when a newer server exists. No silent updates.

## 9. Security

- Same model as today: a server password for new identities; no accounts. The password is shown in the
  console and stored in config.json (the data folder is per-user).
- LiveKit keys are random and never shown.
- Exposing ports to the internet (UPnP/public mode) puts the Nexo server and LiveKit on the public internet
  over plain http/ws. That's today's exposure model for port-forwarded hosts; TLS stays optional (reverse proxy,
  SERVER.md). The setup says so in one sentence and recommends Tailscale when it works for the group.
- Unsigned executables: SmartScreen warns on first run (same as the app installer). SEA binaries are
  sometimes flagged by antivirus; see R2.

## 10. Risks

| # | Risk | Mitigation |
|---|---|---|
| R1 | Node SEA limits (experimental warning, native modules unsupported) | No native modules are needed (C2). Spike first (S0). Fallback: zip with `node.exe` + bundled JS + a tiny launcher |
| R2 | Antivirus false positives on an unsigned SEA exe | Report to vendors; fallback layout from R1; code signing later |
| R3 | CGNAT is common (many ISPs) | Detect it (§6) and route the host to Tailscale with clear steps |
| R4 | UPnP mappings that linger or conflict | Fixed lease time, renewed while running, removed on exit; re-use existing mappings to our own IP |
| R5 | Windows firewall prompts confuse users | Explain before; detect blocked ports on a local self-test |
| R6 | Host upload saturation hurts their own game | Live upload in status, warning, quality suggestion (§7) |

## 11. Open questions

1. **Name/branding** of the download: "Nexo Server" zip vs. an installer. Proposal: zip for v1.
2. **Invite links**: a `nexo://join?server=…` link that opens the app with the server pre-filled (needs a URL
   protocol handler in the desktop app). Proposal: later, separate small change.
3. **Outside reachability check**: use a public port-check service (third party, privacy) or not? Proposal: no;
   rely on UPnP + CGNAT detection + "first remote friend connected".
4. **macOS** builds need LiveKit's macOS binary and Gatekeeper handling; proposal: after Windows and Linux.
5. Should the existing Docker path stay documented? Proposal: yes, as the "advanced / VPS" option in SERVER.md.
